# MLPPP bundle on MultiTech 7910, 4 November 2026

A Windows 95 caller dialling 7910 with multilink enabled raised both B
channels, but the second link was torn down by the client immediately after
authentication. Server logs from 3 November, 22:32–22:37:

```
22:32:15 pppd[58340] Connect: mtppp0 <--> /dev/ttyM4
22:32:35 PAP peer authentication succeeded for scottc
22:32:43 local 10.254.104.1  remote 10.254.104.2     (IPCP up, 21412 bytes sent)
22:34:51 pppd[58341] Connect: mtppp1 <--> /dev/ttyM5
22:34:56 PAP peer authentication succeeded for scottc
22:34:56 LCP terminated by peer
22:36:52 (retry, identical outcome)
22:37:16 mtppp0: No response to 6 echo-requests
```

Cause: the two answerers were independent single-link PPP servers that
happened to share a phone number. `multilink`/`mrru` was absent from
`/etc/ppp/options` and from both peer files, and the peers differed in
`name`, `ifname` and address pair, so no bundle could form. `/run/pppd2.tdb`
had not been written since 24 October, confirming nothing had ever joined a
bundle on this host. The client requests MRRU on the second link, pppd 2.5.2
does not acknowledge it without `multilink`, and the client will not retain
an unbundled extra link.

## Change applied

Both peer files now share `name`, `ifname` and address pair, and both carry
`multilink` with `mrru 1500`.

## Consequence to note

7910 is now a single bundle endpoint. Two unrelated callers can no longer
each hold an independent session on it, since both links answer with the
same interface and the same client address. That capability was already
lost the moment the address pair had to be unified, which a bundle requires.

## The bundle is proven over SIP softmodem calls

Tested with `sip_v90_modem` in Proxmox CT 117 (`v90modem-dev`, 192.168.88.230)
on vmhost, two lines dialling 7910 through `asterisk.net.cryan.nz` as account

```sh

  --sip-server asterisk.net.cryan.nz --username 6002 --password 6002 \
  --local-port 5062 --rtp-port 4200 --pty-link /tmp/mlppp --verbose
# then, per line i, a pppd on /tmp/mlppp.$i

  noauth user scottc password lab multilink mrru 1500 \
  noipdefault nodefaultroute noproxyarp noipv6 noccp novj asyncmap 0
```

`--lines N` re-executes the binary once per line, giving worker *i* SIP port
`5062+i`, RTP `4200+100i` and PTY `/tmp/mlppp.i`. Both workers registered as
6002 and Asterisk accepted both contacts.

The caller logged the mirror image: `New bundle ppp0 created`, then
`Link attached to ppp0`. One interface each side, `10.254.104.1` peer
`10.254.104.2`, two calls up on ttyM4 and ttyM5. So the server configuration
in this document is correct: MRRU and the endpoint discriminator are
exchanged and acknowledged, and a second link joins the existing bundle

### Data over the bundle fails, at the caller

The caller cannot handle MP-encapsulated frames. Every time the server sends
one, the caller answers with a protocol reject:

```
rcvd [proto=0x3d] c0 00 00 00 80 21 01 01 00 0a 03 06 0a fe 68 01
Unsupported protocol 'Multi-Link' (0x3d) received
sent [LCP ProtRej id=0x2 00 3d c0 00 00 00 80 21 ...]
```

The payload in that frame is the server's `IPCP ConfReq`. Two runs:

| Run | Links started | Result |
|---|---|---|
| 1 | staggered, ~2 min apart | IPCP completed after the ProtRej, so the link ran as plain PPP. 6/6 pings at 256 B. 120 pings at 1400 B: **100% loss** |
| 2 | together | `IPCP: timeout sending Config-Requests`, then `LCP TermReq "No network protocols running"`; the bundle tore down |

Run 1's small pings survived because the server had fallen back to
unencapsulated frames on the one link; the 1400-byte pings have to be
fragmented across both links, every packet then needs an MP frame, and all of
them were lost. Run 2 is the honest case: with both links up from the start
the server uses MP throughout and IPCP never completes.

The caller's pppd accepted the `multilink` and `mrru` options, so it is built
with multilink, and the pve kernel reports `CONFIG_PPP_MULTILINK=y`. What is
distinctive about this caller is that CT 117 is an **unprivileged** LXC with
`/dev/ppp` bind-mounted and owned by `nobody:nogroup`. The leading
explanation is that the kernel's MP path (setting MRRU on the unit, or
attaching the channel in MP mode) fails a capability check for a user
namespace whose root is unprivileged in the initial namespace, and pppd does
not log the failure, so MP frames arrive in userspace and get rejected. That
is a hypothesis, not a measurement.

### No user data crosses it

A 16 KiB known pattern sent into the call did not come back. The answerer
counted 359828 bytes in and the same 359828 echoed out, but what reached the
caller was 153211 bytes of which **136556 were 0x7f** — a μ-law zero code.
The pattern is absent under identity, bit inversion, high-bit flip and
nibble swap, so this is not a law or bit-order mismatch to correct; it is
silence.

The Cisco is bridging this as a voice call — G.711 audio with its own idle
and silence handling — not as an unrestricted-digital 64 k bearer. The bytes
the Diva echoes never leave as data, and the bytes the caller sends never
arrive as data. That is the CLEARMODE/UDI mapping the 24 October notes record
as deliberately unchanged, and it is the one thing standing between this
answerer and a working ISDN clear-channel path.

So the ISDN work now stands at: a digital answerer that arms, answers and
reports at 64 k on a reachable number, with the bearer still voice-mapped.

## It was law transcoding, not CLEARMODE: clear channel is byte-exact

Correction to the section above. RFC 4040 CLEARMODE is not needed on this
path and was never the blocker. `v90modem/docs/clear_channel_v120.md` is
explicit: the SIP/G.711 bearer is passed through byte-exact
(`PJMEDIA_HAS_PASSTHROUGH_CODECS`), so every RTP payload octet already *is*
a DS0 octet. What breaks that is a law conversion, and the path had one.

- The Asterisk endpoint the 7950 dialplan uses, `toprouter-bri`, is
  `disallow=all` / `allow=alaw`, commented "Voice-only route for TopRouter
  BRI lines", and the BRI port is A-law.
- The test leg was pinned to mu-law with `SIP_FORCE_PCMU=1`, inherited from
  the modem harness, so Asterisk transcoded mu-law to A-law in the middle.
  `pjsip.conf` warns about exactly this in its own template comments:
  "alaw<->ulaw translation is not byte-exact, so offering both lets a bridge
  silently transcode."

Pinning the caller to A-law instead — `SIP_FORCE_PCMA=1`, a one-word change
on the caller, no PBX edit at all — makes the clear-channel call transparent:

```
sent 16384 received 21042
pattern start found at 4644
aligned bytes compared 16384 matching 16384
```

**16384 of 16384 bytes byte-exact**, echoed back through
`/dev/ttyds5 CONNECT 64000` on Diva controller 4, profile 8 bit-transparent.
The earlier mu-law run returned 136556 bytes of 0x7f out of 153211 — A-law
idle arriving as mu-law zero, which is what a transcode of silence looks
like, and why the pattern was absent under every bit-order transform.

So ISDN clear channel works end to end on this lab, at 64 kbit/s, with no
Cisco or Asterisk change. The rule is that a clear-channel or V.120/V.110
caller on this path must use A-law, because the BRI leg is A-law and any law
conversion destroys the DS0.

Asterisk does have the clearmode format registered
(`47 audio clearmode — RFC 4040 opaque 64 kbit/s DS0`) and the lab's
`endpoint-modem` / `endpoint-modem-alaw` templates already offer
`clearmode,ulaw` and `clearmode,alaw`, so the option exists if a future
device needs genuine RFC 4040 signalling. Should that ever be enabled, note
the trap recorded in `v90modem/docs/apple_usb_modem_sm56.md:1757`: pjsip
parsed `allow=!all,clearmode,ulaw` before `codec_clearmode.so` had
registered its format, and every endpoint built on that template silently
lost clearmode. Check the runtime endpoint, not the config file.

### Where the ISDN work stands

- Clear channel, 64 k, byte-exact, proven: caller in A-law, answerer on
  controller 4 / 7950 / profile 8.
- V.120 and V.110 are the same bearer with framing on top, so they should
  follow from here; untested.
- ISDN PPP needs `"profile": 9` in `/etc/bri-clear/config.json` instead of 8,
  and a pppd over the ttyds port rather than the echo loop.
- A 2x64k MLPPP bundle over ISDN then needs two such calls, which needs the
  caller-side MP reassembly problem solved; an unprivileged LXC cannot do it.

## Profile 9 tried: the framed profiles will not answer this bearer

An ISDN PPP answerer was built and tested — `deploy/ppp/isdn-7950`, a pppd on
`/dev/ttyds5` with its own address pair `10.254.105.1:10.254.105.2`,
`ifname isdnppp0`, `multilink mrru 1500`, and a `pap-secrets` line for the
name `isdn-7950`. Its options follow the vendor's own sample,
`divas4linux-master/contrib/pppd/peers/diva`, which runs **async** pppd over
the ttyds port (`asyncmap 0`, `crtscts`, `modem`) and, notably, already
carries `multilink`. Three profiles were tried, with the caller being a
softmodem line pinned to A-law.

| Answerer profile | Caller mode | Result |
|---|---|---|
| 9, HDLC/PPP | clear (V.14) | **never answered** — no CONNECT reached the chat |
| 8, bit-transparent | clear (V.14) | answered, `CONNECT 64000`; both ends then sent LCP ConfReq and **neither saw the other's** |
| 6, V.120 64k | v120 | **never answered** |

So profiles 9 and 6 decline the call outright. That fits the bearer: the
Cisco presents this as a 3.1 kHz audio call, and the HDLC and V.120 stacks
want an unrestricted-digital bearer. Profile 8 tolerates an audio bearer,
which is why clear channel worked and why it is the only one that answers.

Profile 8 then fails for a different reason, and it is a framing mismatch,
not a transport fault. The pipe is byte-exact — 16384 of 16384 proved that.
But the caller's clear channel always frames what the DTE writes, V.14 by
default or V.42 LAPM with `ME_DATA_FRAMING=lapm`, and `docs/env_knobs.md`
offers only those two values: there is no raw-octet mode. Profile 8 hands
the tty the DS0 octets directly. So the answerer's pppd sees V.14-framed
bits as raw bytes and the caller sees the answerer's async-HDLC bytes
through a V.14 decoder. Each side's ConfReqs are unreadable to the other,
which is exactly what both logs show. The earlier echo test survived because
the Diva echoed the octets verbatim and the caller's own V.14 layer decoded
its own framing back.

Matching the two needs one of:

- **A digital bearer**, so profile 9 answers and the card does HDLC for a
  real ISDN PPP peer. This is the Cisco-side work, and it is also what a 2x64k
  ISDN bundle would need.
- **A raw-octet caller**, writing PPP's async-HDLC bytes straight onto the
  DS0 with no V.14 or LAPM layer. That is a softmodem change, not a
  configuration one.

V.120 on the caller does do HDLC framing and would pair with profile 6, so
that combination is worth retrying the moment a digital bearer exists.

The lab was left in the state that works: `isdn-7950.service` is installed
but **disabled and stopped**, and `bri-clear-answerer` is enabled and active
again, armed `profile=8 controller=4 number=7950`. The ISDN PPP files stay in
the repository for when the bearer question is settled.

## The bearer: the Cisco does map CLEARMODE to a digital call

The softmodem can offer RFC 4040 in SDP — `ME_CLEARMODE=1`, documented in
`v90modem/docs/env_knobs.md` and `clear_channel_v120.md`, default off because
no CLEARMODE gateway had ever been tried. This lab has one.

Account 6002, which the harness uses, allows `opus|g722|alaw|ulaw` and cannot
carry it. Three accounts can: 6004, 6311 and 6312 all allow
`clearmode|ulaw`, and 6004 is the softmodem's own endpoint. On the far side,
the route matters just as much: the 7910 dialplan line dials
`PJSIP/6501/...`, and endpoint 6501 allows `clearmode|ulaw|alaw`, while
7920/7930/7940/7950 all dial `PJSIP/toprouter-bri/...`, which is
`disallow=all` / `allow=alaw`.

So 6004 to 7910 is the one path in this lab where clearmode can be offered
end to end today, and it was tested with a tcpdump of the SIP leg to the
Cisco at 192.168.88.62.

| Call | Offer | Result |
|---|---|---|
| 6004 -> 7910, `ME_CLEARMODE=1` | `m=audio ... RTP/AVP 98 0 8 101` with `a=rtpmap:98 CLEARMODE/8000` | `SIP/2.0 100 Trying`, then **`486 Busy here`, `Reason: Q.850;cause=17`** |
| 6004 -> 7910, `ME_CLEARMODE=0` | PCMU/PCMA only | CONFIRMED, `CONNECT 64000`, analogue carrier on the PTY |

The control is what makes this readable. The same account, the same number,
seconds apart: with clearmode it is rejected, without it the call connects,
so no B channel was busy. And the rejection is **not** a 488 Not Acceptable
Here from the Cisco — the Cisco sent `100 Trying` and then a Q.850 cause 17,
"user busy", which is an **ISDN** cause relayed from the far end. The Cisco
accepted the CLEARMODE offer, placed the ISDN call, and the MultiTech ISI
refused it as busy, which is what an analogue modem card does when handed an
unrestricted-digital bearer.

That is the bearer question answered: the Cisco will present a digital call
when Asterisk offers CLEARMODE. What is missing is a path that offers
CLEARMODE **to a Diva number**, because the Diva is the card that answers
digital calls, and every Diva number routes through the A-law-only
`toprouter-bri` endpoint.

### The one change that would finish this

An additive dialplan entry, in the style of the `17910` diagnostic peer the

 same => n,Dial(PJSIP/6501/sip:7950@192.168.88.62:5060,30)

## PPP crosses the digital call in one direction, and the last blocker is V.14

`ttyds10` and `ttyds11` were removed from `/etc/bri-test/new-spans.json`
(repo copy in `deploy/bri-test/new-spans.json`, original backed up in
`/var/backups/ppp-mlppp-20261104`), so 7950 now has exactly one listener.
7930 on controller 7 and 7920 on controller 8 are untouched and still armed.

With the contention gone, the profile 9 answerer took the digital call:

```
chat:  Nov 04 09:55:25 CONNECT 64000
Starting negotiation on /dev/ttyds5
sent [LCP ConfReq <auth pap> <mrru 1500> <endpoint [MAC:88:51:fb:4f:be:37]>]
rcvd [LCP ConfReq <asyncmap 0x0> <magic 0xb343fa14> <mrru 1500> <endpoint [MAC:bc:24:11:89:d7:3b]>]
sent [LCP ConfAck ...]
```

**The answerer received the caller's LCP ConfReq over a 64 k unrestricted
digital ISDN call and acknowledged it.** That is the first PPP frame this
lab has carried over a digital bearer. The caller, though, never saw the
answerer's frames and timed out.

### What the answer direction actually carries

Reading the caller's PTY raw instead of giving it to pppd, during the same
kind of call:

```
bytes received: 158610
0x7e (PPP flag) count: 79123
async-HDLC LCP header at: -1
top bytes: [(63, 79130), (126, 79123), ...]
first bytes: ATD17950..CONNECT 64000..?~?~?~?~?~?~?~?~
```

The answer direction is not silent and not idle: it is the answerer's pppd
sending HDLC flags, 79123 of them. But every `0x7e` arrives paired with a
spurious `0x3f`, in almost exactly equal counts, and no async-HDLC LCP
header can be found.

That is a V.14 artefact. The caller's clear-channel mode frames the bit
stream as V.14 asynchronous characters — start bit, 8 data bits, stop bit —
so its receiver slices 10-bit groups out of a stream that is octet-aligned
PPP, and each 8-bit flag comes out as two characters. The caller's own
transmit direction worked because the Diva's HDLC receiver found real frames
in it; the receive direction cannot, because nothing on the wire put V.14
framing there.

### The last blocker, precisely

`ME_DATA_FRAMING` accepts only `v14` or `lapm` (`v90modem/docs/env_knobs.md`),
so the softmodem's clear channel always frames. PPP over a digital bearer
needs the DTE's octets placed on the DS0 unchanged. **This is a v90modem code
change — a transparent framing mode for CLEAR — not a configuration change
anywhere in the lab.**

Everything else is proven: the softmodem offers CLEARMODE, Asterisk carries
it on the 17950 route, the Cisco maps it to Bearer Capability 0x8890 and
places the call, the Diva answers it at 64 k with TTY profile 9, and PPP
frames cross caller-to-answerer and are acknowledged.

## Transparent framing added, and what it uncovered

`ME_DATA_FRAMING=transparent` now exists in v90modem (`CC_TRANSPARENT`): one
DTE octet per DS0 octet, MSB first, an all-ones mark when the DTE has
nothing, and restricted 56k refused because bit 1 is robbed. It reuses the
byte callbacks V.120 and V.110 already had, so the data stack's framing is
bypassed entirely. Eight assertions in `clear_channel_test` cover it — octets
exact both ways, mark fill past the source, the 56k refusal, and the PPP flag
and escape passing through untouched — and the 139-test fast tier passes.
Built and deployed into CT 117 as well.

On the live call it engages, and the caller-to-answerer direction still
works:

```
caller:    [ME] DTE framing: transparent (clear channel: one DTE octet per DS0 octet)
answerer:  rcvd [LCP ConfReq ... <mrru 1500> <endpoint [MAC:bc:24:11:89:d7:3b]>]
answerer:  sent [LCP ConfAck ...]
```

The answer direction still does not reach the caller, but the reason has
changed, and it is no longer framing. Reading the caller's PTY raw now:

```
0x7e count: 55822
top bytes: [(249, 71977), (231, 61450), (126, 55822), (159, 47971)]
```

0xf9, 0xe7, 0x7e and 0x9f are all **rotations of 01111110** — the PPP flag
seen at four different bit offsets, in bulk, not one consistent offset. A
fixed misalignment would give one rotation. Four of them, drifting, means
octets are being inserted or dropped in the receive path over the life of the
call: the stream is byte-exact in content but not slip-free.

That also explains why the earlier 16384-of-16384 echo test passed. V.14
re-synchronises on every character's start bit, so it hides small slips; a
transparent octet stream has nothing to resynchronise on and shows them.

So the next thing to chase is sample accounting on the softmodem's RTP
receive path for a synchronous bit pipe, which is exactly what
`v90modem/CLAUDE.md` warns about: "Sample-rate error is fatal. Don't add
buffering that changes sample accounting, and don't splice samples into the
received stream." Everything else in the chain is now proven and committed.

## It is not slip: the answer direction is synchronous HDLC

The receive path was the wrong suspect. RX clock-recovery slips are off by
default — `me_rx_g711_slip_permitted()` returns false unless
`ME_RX_CLOCK_SLIP` is set, and it was not — so nothing was inserting or
dropping samples.

What the four rotations of the flag actually mean is **bit stuffing**. The
Diva's TTY profile 9 puts a synchronous HDLC bit stream on the B channel:
flags, frames, and a zero inserted after every five ones, so the frame body
and each following flag sit at an arbitrary bit offset from the DS0's octet
boundary. Reading that as octets gives 0x7e at every rotation, which is
exactly the measurement.

Decoding the captured stream properly — find the flag at any bit offset,
destuff, and assemble each octet **least-significant bit first**, which is
how HDLC transmits while the DS0 itself is MSB first — resolves it
completely:

```
flags found: 237222   good frames: 10   bad FCS: 0
  frame: ff03c0210105001f0304c0230506  len 35
```

`ff 03` is the PPP address and control, `c0 21` is LCP, `01` a
Configure-Request with id 05 and length 0x001f, `03 04 c0 23` asks for PAP
and `05 06` carries the magic number. That is the answerer's ConfReq,
intact, with a valid FCS-16. The decoder is kept as
`tools/hdlc_bits_decode.py`.

So nothing is lost or corrupted in either direction. The caller simply reads
async framing where the wire carries synchronous framing.

### What that means for the fix

The transparent mode is still right and still needed — it is what lets the
raw bit stream reach a consumer unmodified. What is missing above it is the
conversion an ISDN terminal adaptor does: synchronous HDLC on the B channel,
async HDLC (RFC 1662's octet-stuffed form) on the DTE side. `clear_channel.c`
already drives SpanDSP's `hdlc.c` for V.120, so the machinery is there; what
it needs is a PPP-over-HDLC mode that frames the DTE's packets directly
instead of wrapping them in a V.120 header.

V.120 is not a shortcut around it. Profile 6 was retried now that the bearer
is digital and still refuses the call — only profiles 8 and 9 answer here —
so the caller cannot meet the Diva in V.120 even though both ends implement
it.
