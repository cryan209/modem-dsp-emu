# MLPPP bundle on MultiTech 7910, 4 November 2026

A Windows 95 caller dialling 7910 with multilink enabled raised both B
channels, but the second link was torn down by the client immediately after
authentication. Server logs from 3 November, 22:32–22:37:

```
22:32:15 pppd[58340] Connect: mtppp0 <--> /dev/ttyM4
22:32:35 PAP peer authentication succeeded for scottc
22:32:43 local 10.254.104.1  remote 10.254.104.2     (IPCP up, 21412 bytes sent)
22:34:51 pppd[58341] Connect: mtppp1 <--> /dev/ttyM5
22:34:56 PAP peer authentication succeeded for scottc
22:34:56 LCP terminated by peer
22:36:52 (retry, identical outcome)
22:37:16 mtppp0: No response to 6 echo-requests
```

Cause: the two answerers were independent single-link PPP servers that
happened to share a phone number. `multilink`/`mrru` was absent from
`/etc/ppp/options` and from both peer files, and the peers differed in
`name`, `ifname` and address pair, so no bundle could form. `/run/pppd2.tdb`
had not been written since 24 October, confirming nothing had ever joined a
bundle on this host. The client requests MRRU on the second link, pppd 2.5.2
does not acknowledge it without `multilink`, and the client will not retain
an unbundled extra link.

## Change applied

Both peer files now share `name`, `ifname` and address pair, and both carry
`multilink` with `mrru 1500`.

| Option | multitech-7910 | multitech-7910-b |
|---|---|---|
| Device | `/dev/ttyM4` | `/dev/ttyM5` |
| `name` | `multitech-7910` | `multitech-7910` |
| `ifname` | `mtppp0` | `mtppp0` |
| Addresses | `10.254.104.1:10.254.104.2` | `10.254.104.1:10.254.104.2` |
| `multilink` / `mrru` | present / 1500 | present / 1500 |
| `linkname` / `ipparam` | `multitech-7910` | `multitech-7910-b` |

pppd bundles on the peer's authenticated identity, which is `scottc` on both
links, so no client-side change is needed. The existing `pap-secrets` line
`* multitech-7910 "" 10.254.104.2` covers both links; the `multitech-7910-b`
line and the `10.254.104.6` NAT entry are now unused and were left in place.

| Repository source | Installed on eicon420 |
|---|---|
| `deploy/ppp/multitech-7910` | `/etc/ppp/peers/multitech-7910` |
| `deploy/ppp/multitech-7910-b` | `/etc/ppp/peers/multitech-7910-b` |

Both are root-owned mode 0600; `multitech-7910-b` had been 0644 and was
tightened. Originals are backed up under
`/var/backups/ppp-mlppp-20261104`.

## Consequence to note

7910 is now a single bundle endpoint. Two unrelated callers can no longer
each hold an independent session on it, since both links answer with the
same interface and the same client address. That capability was already
lost the moment the address pair had to be unified, which a bundle requires.

## Verification status

- `pppd dryrun` accepted both peer files; the option dump confirms
  `multilink`, `mrru 1500`, one `name`, one `ifname` and one address pair on
  both links.
- `multitech-ppp.service` and `multitech-ppp-b.service` restarted and are
  active, each holding its own `pppd`. No call was in progress at the time.
- **Not yet tested with a real call.** No bundle has been observed forming;
  that needs a Windows multilink dial-in. The expected evidence is one
  `mtppp0` interface, `/run/pppd2.tdb` updated, and no `LCP terminated by
  peer` on the second link.
- Expected throughput is bounded by this path's history: neither direction
  has sustained better than 31,200, so a working bundle is roughly 62 kbit/s
  less MP fragmentation overhead, and it consumes both B channels.

Unrelated pre-existing fault observed while checking: `multitech-7900.service`
(ttyM6) has been failed since 3 November 22:48:26 with a connect-script
failure, exit status 8. It was already failed before this change and was not
touched; `multitech-7900-b` (ttyM7) is active.

## Eicon channels added as bundle members, same day

A bundle lives in pppd on this host and is matched through `/run/pppd2.tdb`,
so members need not share a card. `ttyds3` and `ttyds4` (Diva controller 1,
number 7910) were converted from test-menu channels into bundle members of
the same 7910 bundle, giving four configured members across two cards.

Three properties of the old path had to change. The Eicon PPP was reached by
typing `7` at the `bri_test_answerer.py` menu, which an MLPPP client will
never do, so these channels now start pppd on connect. It ran `noauth`, and
pppd bundles on the peer's authenticated name, so they now use `require-pap`
with the shared bundle identity. And it assigned `10.254.{90+unit}.1:.2` per
tty, so ttyds3/ttyds4 gave 10.254.93.x and 10.254.94.x; members must all
carry `10.254.104.1:10.254.104.2`.

`name multitech-7910` is reused on all four members. It is the shared bundle
identity and the server name its `pap-secrets` line matches, not a per-card
label. A neutral name would need a new `pap-secrets` entry first; a dry run
with an invented name is rejected with "The remote system is required to
authenticate itself".

| Member | Device | Card | Unit |
|---|---|---|---|
| `multitech-7910` | /dev/ttyM4 | MultiTech BRI A | `multitech-ppp.service` |
| `multitech-7910-b` | /dev/ttyM5 | MultiTech BRI A | `multitech-ppp-b.service` |
| `eicon-7910-c` | /dev/ttyds3 | Diva controller 1 | `eicon-7910-c.service` |
| `eicon-7910-d` | /dev/ttyds4 | Diva controller 1 | `eicon-7910-d.service` |

All four share `name`, `ifname mtppp0`, `multilink`, `mrru 1500` and the one
address pair, and differ only in device, `linkname` and `ipparam`.

The Diva answer init is a chat script mirroring the AT sequence
`bri_test_answerer.py` uses on its own channels: `AT&F14`, `AT+iQ=a1`,
`AT+iA7910`, `AT+MS=V90,1`, `AT\N3%C1`, `ATE0V1S0=1\V1#CID=14`, then wait
for CONNECT. Backslashes are doubled in the chat file.

| Repository source | Installed on eicon420 |
|---|---|
| `deploy/ppp/eicon-7910-c`, `-d` | `/etc/ppp/peers/eicon-7910-{c,d}` |
| `deploy/ppp/eicon-7910-c.service`, `-d.service` | `/etc/systemd/system/` |
| `deploy/ppp/eicon-7910-answer` | `/etc/chatscripts/eicon-7910-answer` |
| `deploy/ppp/eicon-connect` | `/usr/local/lib/ppp-web/eicon-connect` |
| `deploy/bri-test/config.json` | `/etc/bri-test/config.json` |

`eicon-connect` is the ttyds counterpart of `modem-connect`, which accepts
only ttyM names. The test answerer's config now lists ttyds1 and ttyds2
only, so ttyds3 and ttyds4 no longer offer the echo/upload/telnet menu.
The previous config is backed up in `/var/backups/ppp-mlppp-20261104`.

### Verification status

- `pppd dryrun` accepts both new peers, exit 0. Both units are enabled and
  active, each holding its own pppd (61317, 61318), sitting in the chat
  script with no connect-script failure logged.
- The test answerer restarted clean on the two-channel config and released
  both devices: `fuser` reports no owner for ttyds3 or ttyds4.
- **No bundle has formed yet.** Four configured members is not four working
  links; that still needs a multilink client dialling in.
- **Inbound routing to the Eicon span is unverified.** A test call from
  controller 2 `/dev/ttyds6` to 7910 returned `NO DIALTONE`, so it could not
  be established whether an inbound 7910 call reaches Diva controller 1 at
  all. If the Cisco routes 7910 only to the MultiTech BRI, the two new
  members will sit idle and the bundle stays at two links. Either the Cisco
  must hunt 7910 across both spans, or the client's extra devices need the
  number that reaches controller 1.
