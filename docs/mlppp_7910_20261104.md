# MLPPP bundle on MultiTech 7910, 4 November 2026

A Windows 95 caller dialling 7910 with multilink enabled raised both B
channels, but the second link was torn down by the client immediately after
authentication. Server logs from 3 November, 22:32–22:37:

```
22:32:15 pppd[58340] Connect: mtppp0 <--> /dev/ttyM4
22:32:35 PAP peer authentication succeeded for scottc
22:32:43 local 10.254.104.1  remote 10.254.104.2     (IPCP up, 21412 bytes sent)
22:34:51 pppd[58341] Connect: mtppp1 <--> /dev/ttyM5
22:34:56 PAP peer authentication succeeded for scottc
22:34:56 LCP terminated by peer
22:36:52 (retry, identical outcome)
22:37:16 mtppp0: No response to 6 echo-requests
```

Cause: the two answerers were independent single-link PPP servers that
happened to share a phone number. `multilink`/`mrru` was absent from
`/etc/ppp/options` and from both peer files, and the peers differed in
`name`, `ifname` and address pair, so no bundle could form. `/run/pppd2.tdb`
had not been written since 24 October, confirming nothing had ever joined a
bundle on this host. The client requests MRRU on the second link, pppd 2.5.2
does not acknowledge it without `multilink`, and the client will not retain
an unbundled extra link.

## Change applied

Both peer files now share `name`, `ifname` and address pair, and both carry
`multilink` with `mrru 1500`.

| Option | multitech-7910 | multitech-7910-b |
|---|---|---|
| Device | `/dev/ttyM4` | `/dev/ttyM5` |
| `name` | `multitech-7910` | `multitech-7910` |
| `ifname` | `mtppp0` | `mtppp0` |
| Addresses | `10.254.104.1:10.254.104.2` | `10.254.104.1:10.254.104.2` |
| `multilink` / `mrru` | present / 1500 | present / 1500 |
| `linkname` / `ipparam` | `multitech-7910` | `multitech-7910-b` |

pppd bundles on the peer's authenticated identity, which is `scottc` on both
links, so no client-side change is needed. The existing `pap-secrets` line
`* multitech-7910 "" 10.254.104.2` covers both links; the `multitech-7910-b`
line and the `10.254.104.6` NAT entry are now unused and were left in place.

| Repository source | Installed on eicon420 |
|---|---|
| `deploy/ppp/multitech-7910` | `/etc/ppp/peers/multitech-7910` |
| `deploy/ppp/multitech-7910-b` | `/etc/ppp/peers/multitech-7910-b` |

Both are root-owned mode 0600; `multitech-7910-b` had been 0644 and was
tightened. Originals are backed up under
`/var/backups/ppp-mlppp-20261104`.

## Consequence to note

7910 is now a single bundle endpoint. Two unrelated callers can no longer
each hold an independent session on it, since both links answer with the
same interface and the same client address. That capability was already
lost the moment the address pair had to be unified, which a bundle requires.

## Verification status

- `pppd dryrun` accepted both peer files; the option dump confirms
  `multilink`, `mrru 1500`, one `name`, one `ifname` and one address pair on
  both links.
- `multitech-ppp.service` and `multitech-ppp-b.service` restarted and are
  active, each holding its own `pppd`. No call was in progress at the time.
- **Not yet tested with a real call.** No bundle has been observed forming;
  that needs a Windows multilink dial-in. The expected evidence is one
  `mtppp0` interface, `/run/pppd2.tdb` updated, and no `LCP terminated by
  peer` on the second link.
- Expected throughput is bounded by this path's history: neither direction
  has sustained better than 31,200, so a working bundle is roughly 62 kbit/s
  less MP fragmentation overhead, and it consumes both B channels.

Unrelated pre-existing fault observed while checking: `multitech-7900.service`
(ttyM6) has been failed since 3 November 22:48:26 with a connect-script
failure, exit status 8. It was already failed before this change and was not
touched; `multitech-7900-b` (ttyM7) is active.

## Eicon channels added as bundle members, same day

A bundle lives in pppd on this host and is matched through `/run/pppd2.tdb`,
so members need not share a card. `ttyds3` and `ttyds4` (Diva controller 1,
number 7910) were converted from test-menu channels into bundle members of
the same 7910 bundle, giving four configured members across two cards.

Three properties of the old path had to change. The Eicon PPP was reached by
typing `7` at the `bri_test_answerer.py` menu, which an MLPPP client will
never do, so these channels now start pppd on connect. It ran `noauth`, and
pppd bundles on the peer's authenticated name, so they now use `require-pap`
with the shared bundle identity. And it assigned `10.254.{90+unit}.1:.2` per
tty, so ttyds3/ttyds4 gave 10.254.93.x and 10.254.94.x; members must all
carry `10.254.104.1:10.254.104.2`.

`name multitech-7910` is reused on all four members. It is the shared bundle
identity and the server name its `pap-secrets` line matches, not a per-card
label. A neutral name would need a new `pap-secrets` entry first; a dry run
with an invented name is rejected with "The remote system is required to
authenticate itself".

| Member | Device | Card | Unit |
|---|---|---|---|
| `multitech-7910` | /dev/ttyM4 | MultiTech BRI A | `multitech-ppp.service` |
| `multitech-7910-b` | /dev/ttyM5 | MultiTech BRI A | `multitech-ppp-b.service` |
| `eicon-7910-c` | /dev/ttyds3 | Diva controller 1 | `eicon-7910-c.service` |
| `eicon-7910-d` | /dev/ttyds4 | Diva controller 1 | `eicon-7910-d.service` |

All four share `name`, `ifname mtppp0`, `multilink`, `mrru 1500` and the one
address pair, and differ only in device, `linkname` and `ipparam`.

The Diva answer init is a chat script mirroring the AT sequence
`bri_test_answerer.py` uses on its own channels: `AT&F14`, `AT+iQ=a1`,
`AT+iA7910`, `AT+MS=V90,1`, `AT\N3%C1`, `ATE0V1S0=1\V1#CID=14`, then wait
for CONNECT. Backslashes are doubled in the chat file.

`eicon-connect` is the ttyds counterpart of `modem-connect`, which accepts
only ttyM names. The test answerer's config now lists ttyds1 and ttyds2
only, so ttyds3 and ttyds4 no longer offer the echo/upload/telnet menu.
The previous config is backed up in `/var/backups/ppp-mlppp-20261104`.

## Option-level logging enabled

All four bundle members now carry `debug`, so the next call records the full
LCP/PAP/IPCP option exchange and a refused or unanswered MRRU becomes
visible. `/etc/ppp/options` sets `hide-password`, so PAP passwords stay out
of the journal. Installed to all four peer files and all four services
restarted; no call was in progress.

Read the next call's exchange with:

```sh
sudo journalctl -u multitech-ppp -u multitech-ppp-b -u eicon-7910-c -u eicon-7910-d --since "-10 min" | awk '!seen[$0]++'
```

What the trailing `awk` removes is real: every pppd line appears twice in
this host's journal.

### Two calls that failed before this was enabled

4 November 08:03:35 and 08:06:46, both inbound on ttyM4, after `multilink`
was added and before `debug` was: `Serial connection established`, then
`Starting negotiation on /dev/ttyM4`, then `Connection terminated` 37
seconds later with no PAP line at all. On 3 November the same path
authenticated in 20 seconds and completed IPCP. The plain log gives no
reason, which is why `debug` was enabled. Candidates are the client
rejecting or mishandling the MRRU and endpoint-discriminator options pppd
now sends, or the call dropping on its own.

### Origination from the Diva side is unavailable

Two attempts to place a verification call to 7910 from the host returned
`NO DIALTONE` after a clean AT init: controller 2 via `/dev/ttyds6` and
controller 7 via `/dev/ttyds7`. Controller 7 answered inbound V.90 and V.34
calls on 3 November, so this is an origination-path condition, not a dead
span. It means the bundle cannot be verified from this host alone; the next
evidence has to come from a real multilink dial-in.

### Routing finding

7910 no longer reaches Diva controller 1. Over the last 30 days ttyds3
answered 44 calls and ttyds4 two, but neither since 9 October, while ttyM4
logged 1170 serial-connection lines from 25 October onward including today.
The two Eicon members are therefore configured correctly but will not
receive calls on 7910 as it is routed now.

Number-to-endpoint routing is two layers: the Cisco dial-peer selects the
span, and the ISI card itself assigns MSNs to its internal modems, as
`/usr/local/sbin/multitech-7900-route.py` does with `AT*!DN1`, `AT*!EN2`,
`AT*!N2=7900` over ttyM2.

A correction to `hwic_signalling_20261025.md`: the HWIC spans now carry
calls. `bri-new-spans.service` serves controller 4 as 7950 (ttyds10/11),
controller 7 as 7930 (ttyds12/13) and controller 8 as 7920 (ttyds14/15),
and on 3 November controller 7 trained V.90 at 49333:TX/14400:RX while
controller 8 ran a 0-error duplex stream at V.34 31200. Since MLPPP does
not care which number a member answered, pointing members at 7930 and 7920
is a cheaper route to four links than changing how 7910 is routed.

## The bundle is proven over SIP softmodem calls

Tested with `sip_v90_modem` in Proxmox CT 117 (`v90modem-dev`, 192.168.88.230)
on vmhost, two lines dialling 7910 through `asterisk.net.cryan.nz` as account
6002, with a pppd client per line as the caller side. Nothing needed
installing: the container already had the 29 October build and pppd 2.5.2.

```sh
# caller side, in CT 117
env SIP_FORCE_PCMU=1 ./sip_v90_modem --lines 2 \
  --sip-server asterisk.net.cryan.nz --username 6002 --password 6002 \
  --local-port 5062 --rtp-port 4200 --pty-link /tmp/mlppp --verbose
# then, per line i, a pppd on /tmp/mlppp.$i
pppd /tmp/mlppp.$i 115200 nolock local debug \
  connect 'chat -v -t 90 "" "ATD7910" "CONNECT" ""' \
  noauth user scottc password lab multilink mrru 1500 \
  noipdefault nodefaultroute noproxyarp noipv6 noccp novj asyncmap 0
```

`--lines N` re-executes the binary once per line, giving worker *i* SIP port
`5062+i`, RTP `4200+100i` and PTY `/tmp/mlppp.i`. Both workers registered as
6002 and Asterisk accepted both contacts.

### What the bundle did

Both links negotiated MP and were attached to one bundle, on both sides:

```
# ttyM4, then ttyM5, on eicon420
sent [LCP ConfReq <auth pap> <mrru 1500> <endpoint [MAC:88:51:fb:4f:be:37]>]
rcvd [LCP ConfReq <mrru 1500> <endpoint [MAC:bc:24:11:89:d7:3b]>]
rcvd [PAP AuthReq user="scottc"]  ->  PAP peer authentication succeeded
New bundle mtppp0 created          (ttyM4)
Link attached to mtppp0            (ttyM5)
```

The caller logged the mirror image: `New bundle ppp0 created`, then
`Link attached to ppp0`. One interface each side, `10.254.104.1` peer
`10.254.104.2`, two calls up on ttyM4 and ttyM5. So the server configuration
in this document is correct: MRRU and the endpoint discriminator are
exchanged and acknowledged, and a second link joins the existing bundle
instead of raising its own session.

### Data over the bundle fails, at the caller

The caller cannot handle MP-encapsulated frames. Every time the server sends
one, the caller answers with a protocol reject:

```
rcvd [proto=0x3d] c0 00 00 00 80 21 01 01 00 0a 03 06 0a fe 68 01
Unsupported protocol 'Multi-Link' (0x3d) received
sent [LCP ProtRej id=0x2 00 3d c0 00 00 00 80 21 ...]
```

The payload in that frame is the server's `IPCP ConfReq`. Two runs:

| Run | Links started | Result |
|---|---|---|
| 1 | staggered, ~2 min apart | IPCP completed after the ProtRej, so the link ran as plain PPP. 6/6 pings at 256 B. 120 pings at 1400 B: **100% loss** |
| 2 | together | `IPCP: timeout sending Config-Requests`, then `LCP TermReq "No network protocols running"`; the bundle tore down |

Run 1's small pings survived because the server had fallen back to
unencapsulated frames on the one link; the 1400-byte pings have to be
fragmented across both links, every packet then needs an MP frame, and all of
them were lost. Run 2 is the honest case: with both links up from the start
the server uses MP throughout and IPCP never completes.

The caller's pppd accepted the `multilink` and `mrru` options, so it is built
with multilink, and the pve kernel reports `CONFIG_PPP_MULTILINK=y`. What is
distinctive about this caller is that CT 117 is an **unprivileged** LXC with
`/dev/ppp` bind-mounted and owned by `nobody:nogroup`. The leading
explanation is that the kernel's MP path (setting MRRU on the unit, or
attaching the channel in MP mode) fails a capability check for a user
namespace whose root is unprivileged in the initial namespace, and pppd does
not log the failure, so MP frames arrive in userspace and get rejected. That
is a hypothesis, not a measurement.

### What this settles, and what it does not

- The eicon420 bundle configuration works. Two links, two cards' worth of
  endpoints available, one interface, one authenticated peer.
- The whole path works: SIP from CT 117 through Asterisk, the Cisco, the
  MultiTech BRI, modem training, PAP, bundle join.
- MLPPP data throughput is still unmeasured. The caller has to be somewhere
  with working MP reassembly: a privileged container, a real VM, or the
  Windows client, whose own MP stack is the thing that matters anyway.
- ISDN modes were not tested. The CT 117 binary dates from 29 October and its
  `--mode` list stops at the modem modulations; `clear`, `clear56`, `v110`,
  `v120` are in the current tree, so testing those needs a rebuild in 117.
  The answering side would also need a member that takes a 64 k clear-channel
  call — ttyds3 logged `CONNECT 64000` on 8 October, so the Diva will.

The rig was removed afterwards: both client pppds and all softmodem workers
stopped, PTY links deleted, no interface left on either side. On eicon420
`multitech-ppp`, `multitech-ppp-b`, `eicon-7910-c`, `eicon-7910-d` and
`bri-test-answerer` were all active at the end.
