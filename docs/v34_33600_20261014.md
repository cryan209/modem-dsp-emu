# V.34 at 33,600 bit/s — 14 October 2026

The Analog 109 / PRI 117 firmware pair now reaches 33,600 bit/s in both
directions. The 45-second control in
`artifacts/v34-20261014-33600-clock-fixed` passes 10/10 PPP pings with no
retrain, FCS errors or link resets. TX and RX each negotiate 14 bits per
2400-Hz host data tick; `BaudInfo=0x30dd` selects 3429 symbols/s both ways.
The [ADC overflow correction](v34_adc_20261014.md) is also required.

The completed acceptance run, `artifacts/v34-20261014-33600-hold-transfer`,
transfers **1,310,720 bytes (1.25 MiB) over one TCP connection**, with identical
source and receiver SHA-256. All 100/100 PPP pings receive replies. Both ends
remain continuously in DATA for over 558 DSP seconds, with zero PPP FCS errors,
zero link resets, zero retrains, and zero substituted or dropped receive samples.
The full CSV trace retains `BaudInfo=0x30dd` throughout DATA; each mailbox
publishes TX/RX 14-bit datagrams at 2400 Hz (33,600 bit/s).

Extracted logs, trace results, payload hashes and source hashes are saved in
`artifacts/v34-33600-20261014-evidence.json`. The successful capture directory
also retains `source.bin` and `received.bin`, which compare byte for byte.
The caller logs `upload complete bytes=1310720`; the receiver reports the
same byte count after TCP EOF. Both endpoints are then shut down normally.
This is a local emulated loopback result, using the new defaults with no
explicit buffer/hold overrides or firmware quality-control patches.

## Wire clock and measured delay

The transmit loop slept a full packet interval after sending the last queued
packet, even when the next absolute send deadline was sooner. With a
one-packet buffer, send work accumulated into every packet period, slowed
the wire clock and increased the measured round-trip delay.

The loop now waits until `next_send` when that deadline is in the future.
An already overdue, empty queue still uses the existing packet-interval
backoff. A deterministic regression models a 6-ms send cost: a 20-ms
period must then wait 14 ms, while an overdue queue backs off for 20 ms.

The original 160-ms transmit cushion also adds too much round-trip delay
for the firmware's highest symbol rate. INFO code at PM `0x3922..0x3927`
disables 3429 symbols/s when compensated DM `0x3fc9` reaches `0x0118`
(280 ticks at 2400 Hz, or 116.667 ms). The original strict-33600 probe
measured 862 ticks and selected 3200 symbols/s; a 20-ms cushion with the
old wire clock still measured 670 ticks. After the clock correction, the
20-ms control measured 142 ticks and successfully selected 3429 symbols/s.

`eicon_loopback.py` now defaults to a 20-ms transmit cushion for each end
explicitly selecting V.34, including global, per-end and inherited environment
selection. Other modulations retain 160 ms. An explicit `--tx-buffer-ms`
continues to override either default. The firmware's rate and quality
controls remain enabled; there is no patch to its delay threshold.

The V.34 receive hold now defaults to 500 ms, rather than 60 ms. This is
a deadline for an empty receive queue, not added playout latency: fresh
audio resumes the modem as soon as the existing jitter margin is available.
The host measured stalls up to 275 ms, and the failed run's RTP capture
contains an incoming gap of 297.7 ms. In the second long run, the receiver
substituted silence immediately before fast retraining (0 -> 160 -> 255
substituted samples in the final trace window). A regression models a 275-ms
stall and confirms the default waits for the original samples; permanent
loss remains bounded by the hold timeout. Other modulations retain 60 ms,
and an explicit `--rx-hold-ms` overrides either default.

## Large-transfer reproduction

The first 33,600 large-file run reached 1,121,920 bytes but fast-retrained
at about 476 DSP seconds. Its TCP stream closed incomplete; it is not a pass.
The mailbox only suspended LAPM below training state `0xb0`, missing the
fast-retrain path `0xbd -> 0xc6 -> 0xcc -> 0xd0`. LAPM exhausted T401 and
re-established or disconnected even though the physical modem returned.

For an already active V.34 link, the mailbox now keeps LAPM suspended whenever
the modem is outside DATA, or its CTS/RFS and DCD/RSD readiness bits are absent.
This preserves pending sequenced payload and waits for actual receiver readiness
before restarting recovery timers. The V.32 and V.90 state gates are unchanged.
Two new regressions cover the captured ladder and a real LAPM endpoint retaining
unacknowledged payload beyond its ordinary recovery budget.

The second attempt, `artifacts/v34-20261014-33600-recovery-transfer`, retained
the LAPM link through the fast-retrain ladder, but still failed after silence
substitution: the receiver closed with 1,262,480 bytes. It is also incomplete.
The receive hold correction addresses the host stall that preceded that
physical disturbance.

The acceptance run uses one 1.25-MiB TCP payload, 1,310,720 bytes:

```python
from pathlib import Path
import hashlib
Path('/private/tmp/v34-large-payload.bin').write_bytes(
    hashlib.shake_256(b'modem-dsp-emu V.34 large transfer 2026-10-14')
    .digest(1310720))
```

Expected SHA-256:
`48dfa8377510f728c2282d62954449173146af974bde26566c5253ce2ca7cf22`.

Start the receiver in another terminal:

```sh
python tools/tcp_file_sink.py /private/tmp/v34-33600-hold-received.bin --port 47905
```

Then run:

```sh
python tools/eicon_loopback.py --python /Users/scottcryan/v90modem/.venv/bin/python \
  --seconds 1000 --caller-firmware-set analog109 --answerer-firmware-set pri117 \
  --modulation v34,0,33600,33600,33600,33600 --caller-kernel-dispatch \
  --ppp --ppp-ping peer --ppp-ping-count 100 \
  --ppp-tcp-upload /private/tmp/v34-large-payload.bin --ppp-tcp-port 47905 \
  --trace-retrain --sip-port 5190 --rtp-port 4130 \
  --capture-dir artifacts/v34-20261014-33600-hold-transfer
```

The earlier long 31,200 run with the old wire clock retrained late and
closed with only 1,146,960 bytes received. That incomplete transfer is
not a successful large-file result.
