# V.34 data mode carried payload once T401 outlasted the round trip, 23 October 2026

**The loopback reaches data mode and now carries IP.** The documented V.34
19200 command reached `TrnProgress 0x00d0` on both ends and then lost the call
about a second later to a V.42 `FRMR`. The modem layer was never at fault: the
host V.42 T401 was shorter than the link's own round trip. With the default
raised the same command establishes LAPM once, brings up CHAP and IPCP, and
answers every ping with **zero FCS errors and zero data-link resets**.

## What went wrong

T401 has no wall clock — it counts datagrams taken from the LAPM endpoint,
because the bit pipe is clocked by the data pump and the harness can run far
from real time. At V.34 19200 with 8 bits per datagram the link takes 2,400 a
second, so `eicon_adsp_sip.py`'s shipped `retransmit_after=1200` was **500 ms**.

The real round trip is longer. The media jitter buffer alone held about 380 ms
each way, and once PPP was up the pings measured **692–743 ms**. So T401 always
expired before the first `UA` could return:

1. The originator sent `XID` + `SABME(P)` and armed T401.
2. T401 expired at 500 ms and it retransmitted `SABME(P)`.
3. The answerer had already answered the first one, connected as link 1, and
   put an I frame on the wire for its PPP server.
4. A `SABME` in the connected state is a re-establishment request, so the
   answerer answered, reset `V(S)` to 0 and became link 2 — correct per V.42.
5. The originator, which saw one `UA`, acknowledged that pre-reset I frame with
   `N(R)=1`. Against the answerer's new `V(S)=0` that is an invalid `N(R)`.
6. The answerer sent `FRMR`, then `DISC`, and the call ended by V.42 link
   failure one second after reaching data mode.

Every step there is the specification behaving as written. The only defect is
the timer being scaled below one round trip.

## The change

`tools/eicon_adsp_sip.py` now defaults `retransmit_after` to **3600** — 1.5 s at
this rate, twice the measured worst case — still overridable with
`EICON_V42_RETRANSMIT_AFTER`. `N400` stays at 10, so a genuinely dead link is
declared within 15 s.

## Evidence

Three 45-second runs of the same command, differing only in T401:

| T401 | Data mode | LAPM | PPP | Pings | Outcome |
|---:|---:|---|---|---:|---|
| 1200 (shipped) | 0x00d0 at 18.34 s | link 1 **then link 2** | `lcp=closing`, never up | — | **FRMR**, call dead at 20.1 s |
| 7200 | 0x00d0 at 18.56 s | link 1 only | CHAP + IPCP up | 16 replies | ended by shutdown |
| 3600 (new default) | 0x00d0 at 14.50 s | link 1 only | CHAP + IPCP up | **20/20** | ended by shutdown |

A fourth run on the committed default, with no environment override, reached
`0x00d0` at 18.12 s, established once and answered 17 of 20 before the 45 s
window closed. The ping count tracks how much of the window is left after
training, which varies run to run between about 14.5 s and 18.5 s; it is not a
function of this change. Negotiated rate was 19200 bit/s both directions in
every run. Captures are under
`artifacts/dsp-conformance-20261023/v34-data-mode/`.

Five tests in `tests/test_v42_lapm.py` pin the mechanism from frames alone, with
no timing simulation: that T401 is counted in datagrams taken and fires at
exactly `retransmit_after`; that 3600 survives the measured 743 ms; that a
duplicate `SABME` resets `V(S)` on a connected endpoint; that an in-flight
acknowledgement arriving after that reset kills the link with `FRMR`; and that
the same acknowledgement without the duplicate is accepted normally.

```sh
PY=/Users/scottcryan/v90modem/.venv/bin/python
$PY -u tools/eicon_loopback.py --python $PY --seconds 45 \
  --caller-firmware-set analog109 --answerer-firmware-set pri117 \

  --trace-retrain --capture-dir artifacts/v34-data-mode
```

`EICON_V42_RETRANSMIT_AFTER=1200` reproduces the `FRMR` failure.

The interpreter matters: `/tmp/eicon-v34fax-venv` in `profiles.toml` has been
reaped, so `profiles.local.toml` now points `python` at the durable
`/Users/scottcryan/v90modem/.venv`, which carries unicorn 2.1.4. Under that
interpreter the whole suite passes — **895 tests, no failures**. Under a bare
`python3` seven modules cannot import unicorn and fail to load; that is the
interpreter, not breakage.

## Scope

This is the local Analog/PRI loopback, both ends emulated, over local RTP. It
is not a call over a real line and not the physical card — the DSP tone and
routine work on spare SN12196 is separate. The T401 scaling is still in
datagrams, so its wall time varies with the modulation's datagram rate; a
slower modulation gets a proportionally longer T401 from the same constant.
Whether the other modulations' round trips fit inside 3600 at their own rates
is untested here. The ~380 ms each-way jitter buffer that forces this is itself
worth questioning, and reducing it would be the better fix.
